# KeepGo Prototype · v1 PL 미팅 및 코드 리뷰 대비

> 기준 코드: `Desktop/KeepGo/prototype`, `Desktop/KeepGo/v1`  
> 목적: 구현 현황을 설명하고, 기술 선택의 이유와 미확정 정책을 PL·리뷰어에게 확인받기 위한 문서

---

## 1. 한 문장 소개

KeepGo는 YouTube 좋아요 영상에서 장소·이벤트를 정리하고, 사용자의 지역·날짜·시간·취향 조건에 맞는 외출 코스를 추천해 저장된 관심사를 실제 방문 계획으로 연결하는 서비스입니다.

## 2. 이번 리뷰에서 확인받을 것

1. Prototype에서 검증한 사용자 흐름을 v1 구조로 옮긴 방향이 적절한가?
2. Next.js, TanStack Query, Zustand, MSW의 책임 분리가 적절한가?
3. Google OAuth와 토큰 저장·재발급 정책은 백엔드 계약과 일치하는가?
4. 추천 생성의 `202 → 폴링 → 완료` 흐름을 유지할 것인가, SSE로 변경할 것인가?
5. 지역 검색을 법정동까지만 제공할 것인가, 상권·역명·행정동까지 확장할 것인가?
6. 현재 프론트가 임시로 정의한 API 필드를 백엔드·AI 명세에 포함할 것인가?
7. MVP 완료 기준과 필수 E2E 시나리오는 무엇인가?

## 3. Prototype과 v1의 역할

| 구분      | Prototype                           | v1                                            |
| --------- | ----------------------------------- | --------------------------------------------- |
| 목적      | 화면, 문구, 이동 흐름을 빠르게 검증 | 실제 서비스 구조와 API 연동 기반 마련         |
| 기술      | HTML, CSS, JavaScript               | Next.js App Router, React, TypeScript         |
| 데이터    | 자체 Mock API                       | MSW가 실제 HTTP 요청을 가로채 응답            |
| 상태      | 화면 내부 전역 객체 중심            | 서버 상태는 TanStack Query, UI 상태는 Zustand |
| 라우팅    | 자체 해시 라우터                    | Next.js 파일 기반 라우팅                      |
| 검증 대상 | UX와 예외 화면                      | 타입, API 계약, 상태 전이, 빌드·배포 구조     |

### 예상 질문: Prototype이 있는데 왜 v1을 다시 만들었나요?

> Prototype은 사용자 흐름을 빠르게 검증하기 위한 코드라서 실제 API 연결, 타입 안정성, 라우팅, 서버 상태 캐싱과 배포 구조가 부족했습니다. v1에서는 검증된 UI를 유지하면서 Next.js와 TypeScript 기반으로 책임을 분리했습니다. Prototype은 폐기 대상이 아니라 v1의 시각적 회귀를 확인하는 기준으로 남겼습니다.

## 4. v1 구조 요약

```text
화면·사용자 이벤트
    ↓
Feature 컴포넌트
    ├─ TanStack Query hooks ─→ API client ─→ MSW 또는 Spring API
    └─ Zustand store ────────→ 팝업·대화·온보딩 등 UI 상태

API 오류
    ↓
RFC 9457 Problem Details
    ↓
code 기반 문구·재로그인·재시도 처리
```

### 코드 탐색 순서

1. `src/app/(app)/layout.tsx` — 로그인 이후 공통 셸
2. `src/app/providers.tsx` — QueryClient, MSW, 토스트, 세션 만료
3. `src/lib/api/client.ts` — API 공통 요청, Bearer 토큰, 401 재발급
4. `src/lib/api/problems.ts` — 오류 코드별 UI 처리
5. `src/features/*/queries.ts` — 기능별 서버 요청
6. `src/features/recommendations/CoursePopup.tsx` — 핵심 코스 추천 흐름
7. `src/features/recommendations/courseStore.ts` — 추천 UI 상태
8. `src/lib/address/*` — 법정동 검색과 주소 공급자
9. `src/mocks/handlers.ts` — API 명세 기반 Mock 응답

## 5. 기술 선택과 답변 준비

### 5.1 Next.js App Router

선택 이유:

- 파일 기반 라우팅과 중첩 레이아웃으로 모바일 앱 셸을 일관되게 유지합니다.
- 로그인 전·후 레이아웃을 분리하기 쉽습니다.
- Node 런타임 컨테이너와 `output: "standalone"` 배포 방향을 지원합니다.
- 추후 BFF가 필요하면 Route Handler를 추가할 여지가 있습니다.

주의점:

- 현재 주요 화면은 사용자 로그인 이후의 상호작용 화면이라 대부분 Client Component입니다.
- SEO나 초기 서버 렌더링 이점은 크지 않습니다.
- `/api/*`는 Nginx에서 Spring으로 전달하므로 Next Route Handler를 만들 경우 `/bff/*`처럼 별도 prefix가 필요합니다.

예상 질문:

> 왜 일반 React SPA가 아니라 Next.js인가요?

답변:

> 현재 화면은 SPA 성격이 강하지만 팀의 Node 컨테이너 배포 결정, 파일 라우팅, 공통 레이아웃, 추후 BFF 확장 가능성을 고려했습니다. 다만 모든 화면을 무조건 Server Component로 만들지는 않았고, 로그인 이후 사용자별 상호작용 화면은 Client Component로 유지했습니다.

### 5.2 TypeScript

선택 이유:

- BE-FE API 명세의 요청·응답 구조를 타입으로 고정할 수 있습니다.
- 추천 상태, 빈 결과 사유, 오류 코드처럼 경우의 수가 많은 흐름을 안전하게 다룹니다.
- Mock과 실제 API가 같은 타입을 사용하도록 만들어 교체 비용을 낮춥니다.

답변:

> TypeScript의 목적은 단순 자동완성이 아니라 API 계약이 바뀌었을 때 영향을 컴파일 단계에서 찾는 것입니다. 특히 추천 응답의 후보·컴포넌트 구조와 nullable 좌표를 명시적으로 관리하는 데 필요했습니다.

### 5.3 TanStack Query

담당하는 상태:

- 사용자 정보, 장소, 이벤트, 보관함처럼 서버에서 가져오는 데이터
- 추천 생성·조회·취소 mutation
- 추천 완료 여부 폴링
- mutation 이후 캐시 무효화

선택 이유:

- 로딩·성공·오류·재시도 상태를 직접 중복 구현하지 않아도 됩니다.
- 추천 생성이 즉시 끝나지 않기 때문에 `retryAfterSeconds`를 따르는 폴링이 필요합니다.
- 서버 데이터와 UI 상태를 분리할 수 있습니다.

예상 질문:

> 모든 상태를 Zustand 하나로 관리하면 안 되나요?

답변:

> 가능하지만 서버 데이터에는 캐시 수명, 재조회, 중복 요청 제거, mutation 후 무효화 같은 문제가 따라옵니다. 이 책임은 TanStack Query에 두고, Zustand는 서버와 무관한 UI 상태만 관리했습니다.

### 5.4 Zustand

담당하는 상태:

- 코스 추천 팝업 열림 여부
- 진행 중 대화와 추출 조건
- 온보딩 선호도
- Toast·Confirm·Sheet 같은 전역 UI

선택 이유:

- 여러 화면 위에 겹쳐 뜨는 코스 추천 팝업은 특정 페이지의 지역 상태로 두기 어렵습니다.
- Context를 여러 단계 전달하는 prop drilling을 피할 수 있습니다.
- Redux보다 필요한 코드가 적고 상태 전이가 단순합니다.

주의점:

- 서버 응답까지 Zustand에 복제하지 않습니다.
- 영구 보존할 상태와 현재 세션에서만 유지할 상태를 구분해야 합니다.

### 5.5 MSW

선택 이유:

- 컴포넌트에 더미 배열을 직접 넣지 않고 실제 `fetch` 요청과 같은 경로를 테스트합니다.
- 백엔드가 준비되지 않아도 로딩, 성공, 빈 결과, 400·401·409·500을 재현할 수 있습니다.
- 실제 API 연결 시 `NEXT_PUBLIC_USE_MOCK=false`로 전환하고 화면 코드는 유지할 수 있습니다.

예상 질문:

> 단순 JSON 더미 데이터와 무엇이 다른가요?

답변:

> JSON 더미는 화면 렌더링만 확인하지만 MSW는 URL, HTTP method, 요청 body, 상태 코드, 지연 시간과 오류 응답까지 흉내 냅니다. 따라서 API 연결 이전에도 실제 네트워크 경계에 가까운 테스트가 가능합니다.

### 5.6 RFC 9457 Problem Details와 `code` 기반 분기

선택 이유:

- 같은 401이어도 액세스 토큰 만료와 리프레시 토큰 부재의 후속 행동이 다릅니다.
- HTTP 상태만으로는 사용자 문구와 재시도 가능 여부를 정확히 결정하기 어렵습니다.
- 오류 처리 로직을 화면마다 복제하지 않고 `problems.ts`에 모읍니다.

답변:

> status는 오류의 큰 범주이고, code는 클라이언트가 수행해야 할 구체적 행동을 나타냅니다. 화면은 `code`를 기준으로 재로그인, 재시도, 필드 오류를 구분합니다.

### 5.7 코스 추천을 팝업·바텀시트로 구현한 이유

- 어느 탭에서도 추천을 시작할 수 있습니다.
- 추천 도중 기존 화면 맥락을 잃지 않습니다.
- 조건 수정, 후보 목록, 후보 상세를 같은 Sheet 패턴으로 연결합니다.
- 모바일 화면에서 한 손 조작과 뒤로가기가 자연스럽습니다.

현재 정책:

- 일반 진입은 항상 인트로 화면에서 시작합니다.
- 사용자가 진행 중 대화를 직접 닫은 경우에만 재진입 시 이어집니다.
- 페이지 이동, 추천 완료, 보관함 이동 후에는 초기화합니다.
- 새 대화 시작 시 서버 대화 기록도 함께 초기화합니다.

### 5.8 추천 생성에 202와 폴링을 사용한 이유

```text
POST /recommendations → 202 + runId
GET /recommendations/{runId}
    ├─ 미완료: 409 + retryAfterSeconds
    └─ 완료: 후보 목록
```

답변:

> AI 추천은 수 초 이상 걸릴 수 있어 요청 하나를 오래 유지하면 타임아웃과 사용자 경험 문제가 생깁니다. 작업 생성과 결과 조회를 분리하고, 서버가 준 재시도 간격을 따라 조회하도록 구성했습니다. SSE가 최종 결정되면 조회 hook의 전송 방식만 교체하고 화면 상태 모델은 유지할 수 있습니다.

### 5.9 Node 런타임 컨테이너

선택 이유:

- Cloud 결정에 따라 정적 export가 아니라 Next.js Node 서버로 실행합니다.
- `output: "standalone"`으로 런타임에 필요한 파일만 이미지에 포함할 수 있습니다.
- Nginx는 `/`를 Next.js로, `/api/*`를 Spring Boot로 전달합니다.

리뷰 확인 사항:

- `/_next/static/*` 장기 캐시
- `/healthz` 헬스체크
- Node 컨테이너 메모리
- `/api/*` SSE의 buffering과 timeout

## 6. 인증 설계

현재 구현:

- `Authorization: Bearer <accessToken>`
- 토큰은 메모리와 `localStorage`에 보관
- 401 `AUTHENTICATION_REQUIRED` 발생 시 refresh를 한 번 시도
- refresh 실패 시 세션을 지우고 로그인 화면으로 이동
- 동일 시점의 여러 401이 refresh 요청을 중복 발생시키지 않도록 API 계층에서 처리

예상 질문:

> 왜 HttpOnly Cookie가 아니라 localStorage인가요?

답변:

> 현재 BE-FE 명세가 Bearer 토큰을 프론트가 헤더에 실어 보내는 구조라 그 계약에 맞췄습니다. 하지만 localStorage는 XSS 발생 시 토큰 탈취 위험이 있으므로 최종 인증 정책에서 HttpOnly Cookie 방식과 비교 검토가 필요합니다. 현재 선택을 보안상 최선이라고 주장하기보다 명세 기반의 임시 결정이라고 설명하는 것이 정확합니다.

Backend 확인 사항:

- refresh 요청이 body의 `refreshToken`을 받는지
- access·refresh token 수명
- refresh token rotation 여부
- 동시 401 처리 정책
- 로그아웃 시 서버 refresh token 폐기 여부

## 7. 지역 검색 구현과 발견된 문제

### 7.1 요구사항

- 두 글자 이상 입력 시 자체 지역 DB 검색
- 행정표준코드관리시스템의 법정동 코드 전체자료 사용
- 결과를 `시군구 읍면동` 형태로 표시

### 7.2 현재 구현

- 폐지되지 않은 법정 읍·면·동 5,064건을 정적 TypeScript 데이터로 생성
- `src/lib/address/legalDongData.ts`에 저장
- `scripts/build-region-db.mjs`로 공식 원본을 다시 변환 가능
- 검색 결과 최대 50건
- 정렬 우선순위:
  1. 읍면동 정확 일치
  2. 읍면동 앞부분 일치
  3. 시군구 정확 일치
  4. 시도 축약어와 시군구 조합 일치
  5. 포함 검색
- `서울 중구`, `경기 광주` 같은 시도 축약 검색 지원
- `중구`처럼 같은 이름이 여러 지역에 있으면 시도명을 붙이고 지역별 결과를 번갈아 표시

### 7.3 왜 `행궁동`, `홍대`, 역명은 검색되지 않나요?

데이터 종류가 다르기 때문입니다.

| 사용자가 입력하는 이름 | 실제 분류     | 법정동 DB 검색 가능 여부 |
| ---------------------- | ------------- | ------------------------ |
| 성수동1가              | 법정동        | 가능                     |
| 이태원동               | 법정동        | 가능                     |
| 행궁동                 | 행정동        | 불가능                   |
| 홍대                   | 상권·통칭     | 불가능                   |
| 서촌                   | 상권·통칭     | 불가능                   |
| 홍대입구역             | 지하철역·장소 | 불가능                   |
| 경복궁                 | 랜드마크·장소 | 불가능                   |
| 서울대학교             | 기관·장소     | 불가능                   |

법정동 DB는 행정구역 코드 데이터입니다. 사용자가 약속 장소를 표현할 때 사용하는 상권명, 역명, 학교, 랜드마크 데이터는 포함하지 않습니다. 따라서 검색 알고리즘만 개선해도 존재하지 않는 이름을 찾을 수는 없습니다.

### 7.4 중복 지역명 문제

문제 예시:

- `중구`는 서울, 부산, 대구, 대전, 울산 등에 존재합니다.
- 기존 정렬은 한 지역의 읍면동이 결과 50건을 먼저 채워 다른 지역이 보이지 않았습니다.
- `서울 중구`는 원본이 `서울특별시 중구`라 단순 문자열 검색으로 일치하지 않았습니다.

적용한 해결:

- 시도 축약어 사전 적용: `서울` → `서울특별시`, `경기` → `경기도`
- 중복 시군구 결과에 시도명 표시
- 같은 시군구 이름은 지역별 round-robin 방식으로 분산 배치
- 사용자가 시도를 함께 입력하면 해당 지역만 필터링

### 7.5 현재 방식의 한계

1. 데이터 파일이 클라이언트 번들에 포함됩니다.
2. 원본 갱신 시 빌드 스크립트를 다시 실행해야 합니다.
3. 법정동 원본에는 좌표가 없습니다.
4. 상권·행정동·역명·랜드마크는 검색할 수 없습니다.
5. 상권 범위는 명확한 행정 경계가 아니므로 하나의 법정동으로 단순 치환하면 오해가 생길 수 있습니다.

### 7.6 개선 대안 비교

| 대안                      | 장점                        | 단점                                | 적합한 단계              |
| ------------------------- | --------------------------- | ----------------------------------- | ------------------------ |
| 법정동만 유지             | 요구사항과 데이터가 명확함  | 사용자의 자연어 장소 표현을 놓침    | 최소 v1                  |
| 대표 상권 별칭 사전       | 빠르고 결과 통제 가능       | 수동 관리, 누락 가능                | MVP 추천                 |
| 행정동 DB 추가            | 행궁동 같은 검색 해결       | 법정동과 매핑 규칙 필요             | MVP                      |
| 카카오·네이버 키워드 검색 | 역·학교·랜드마크·상권 지원  | 비용·쿼터·키 관리, 결과 후처리 필요 | MVP 이후 또는 필요 시 v1 |
| Backend 통합 검색 API     | 정책과 랭킹을 한곳에서 관리 | 백엔드 개발 필요                    | 정식 서비스 추천         |

### 7.7 권장안

단계적으로 구성합니다.

```text
1순위: 법정동 정확·접두 검색
2순위: 관리되는 지역 별칭 사전
3순위: 장소 키워드 검색 API
4순위: 현재 위치 기준 거리·인기도로 재정렬
```

별칭 예시:

```ts
const AREA_ALIASES = {

    aliases: ["홍대", "홍대거리", "서교동"],
  },
  서촌: {
    canonicalName: "경복궁역",
    region: "서울 종로구",
    aliases: ["서촌", "통인동", "효자동"],
  },
  용산: {
    canonicalName: "용산역",
    region: "서울 용산구",
```

주의할 점:

- 별칭은 법정동을 대체하는 데이터가 아니라 검색 진입점입니다.

- `홍대 = 서교동`처럼 하나로 강제 치환하기보다 대표 좌표와 범위를 별도로 정의하는 편이 안전합니다.

## 8. 지도 구현

실제 v1 코드는 네이버 지도 API v3를 동적으로 불러옵니다.

- 환경변수: `NEXT_PUBLIC_NAVER_MAP_CLIENT_ID`
- 지도 스크립트는 한 번만 로드하고 Promise를 재사용합니다.
- 후보 장소 좌표로 마커와 경로선을 표시합니다.
- 키 누락, 로드 실패, 좌표 누락 시 SVG 도식으로 fallback합니다.
- 서버 렌더링 시 `window` 접근을 피하기 위해 클라이언트에서만 로드합니다.

리뷰 확인 사항:

- README 일부에는 Leaflet 설명이 남아 있어 실제 구현과 문서를 맞춰야 합니다.
- 추천 응답의 장소 좌표가 아직 BE-FE 명세에 확정됐는지 확인해야 합니다.
- 지도 API 도메인 등록과 운영 키 관리가 필요합니다.

## 9. 코드 리뷰에서 나올 가능성이 높은 질문

### Q1. 왜 모든 화면이 Client Component인가요?

로그인 이후 사용자별 데이터와 상호작용 중심이라 SSR의 SEO·공유 캐시 이점이 작고, 토큰도 현재 브라우저 저장소에 있습니다. 다만 공개 랜딩 페이지가 추가되면 Server Component를 우선 검토해야 합니다.

### Q2. TanStack Query와 Zustand의 경계는 무엇인가요?

서버가 원본인 데이터는 Query, 화면에서만 의미가 있는 상태는 Zustand입니다. 같은 데이터를 두 저장소에 중복하지 않는 것을 원칙으로 합니다.

### Q3. MSW를 제거하면 화면 수정이 필요한가요?

API 명세가 동일하다면 환경변수로 MSW만 비활성화합니다. 응답이 명세와 다르면 화면보다 타입·API 어댑터를 먼저 수정합니다.

### Q4. 추천 폴링 중 컴포넌트를 닫으면 어떻게 되나요?

Query의 enabled 조건과 팝업 phase로 조회를 중단합니다. 정식 서비스에서는 서버 작업 자체를 취소할지, 화면 조회만 멈출지 정책 확인이 필요합니다.

### Q5. 왜 오류를 status가 아닌 code로 처리하나요?

상태 코드는 범주만 표현합니다. 동일한 401·409도 재로그인, 재시도, 진행 중 안내 등 행동이 달라 구체적인 code가 필요합니다.

### Q6. 지역 데이터 5,064건을 왜 프론트에 넣었나요?

백엔드 없이 요구사항을 검증하고 네트워크 요청 없이 즉시 자동완성을 제공하기 위한 v1 선택입니다. 데이터 증가, 갱신, 통합 랭킹을 고려하면 정식 서비스에서는 Backend 검색 API로 이동하는 것이 적절합니다.

### Q7. 검색 결과가 최대 50건인 이유는 무엇인가요?

모바일에서 지나치게 긴 DOM 목록을 만들지 않고 선택 가능한 범위로 제한하기 위해서입니다. 최종값은 UX 테스트와 검색 API 페이지네이션 정책으로 확정해야 합니다.

### Q8. React Hook Form과 Zod는 어디에 사용하나요?

현재 의존성에는 있으나 핵심 화면에서 실질적으로 사용되지 않습니다. 프로필·인증 폼에 일관되게 도입하거나, 사용 계획이 없다면 번들·관리 비용을 줄이기 위해 제거해야 합니다. 사용하지 않은 기술을 사용했다고 설명하면 안 됩니다.

### Q9. Tailwind를 사용하나요?

설정과 의존성은 있지만 현재 UI의 중심은 Prototype에서 옮긴 CSS token과 BEM 형태 클래스입니다. Tailwind는 핵심 선택이라고 설명하기보다 정리 대상 또는 제한적 보조 도구라고 설명하는 것이 정확합니다.

### Q10. 현재 위치와 지역 검색 결과의 좌표가 왜 다르게 처리되나요?

법정동 원본에는 좌표가 없습니다. 현재 위치는 역지오코딩 결과를 DB와 맞추고, 일반 텍스트 검색 결과의 좌표는 nullable로 둡니다. 추천 API가 좌표를 필수로 요구한다면 백엔드 지오코딩 또는 좌표가 포함된 별도 지역 데이터가 필요합니다.

## 13. 1분 설명 대본

> Prototype에서는 로그인부터 온보딩, 좋아요 분석, 홈, 코스 추천, 보관함까지 전체 사용자 흐름을 먼저 검증했습니다. 이후 v1에서는 이 흐름을 Next.js와 TypeScript 구조로 옮겼습니다. 서버 데이터는 TanStack Query, 코스 추천처럼 화면에만 필요한 상태는 Zustand로 분리했고, 백엔드가 준비되기 전에도 실제 요청 구조를 테스트할 수 있도록 MSW를 사용했습니다. 추천 생성은 처리 시간이 길 수 있어 202 응답으로 작업을 만들고 서버가 알려준 간격에 따라 결과를 조회하도록 구성했습니다. 지역 검색은 기능정의서 기준으로 법정동 5,064건을 적용하고 중복 지역명도 구분했습니다. 다만 법정동 데이터에는 행궁동 같은 행정동, 홍대 같은 상권명, 역명과 랜드마크가 없기 때문에 이 부분은 검색 로직이 아니라 데이터 범위의 문제입니다. MVP에서는 법정동 검색을 기본으로 두고 대표 별칭 사전과 장소 키워드 검색 API를 단계적으로 결합하는 방향을 논의하고 싶습니다.
